== 📁 Decision 001 — PicoContainer : rejet assumé de la DI conteneur

_Date_ : 4 août 2026  
_Statut_ : ✅ ADOPTÉE (choix technique assumé)  
_Alternative considérée_ : PicoContainer, Koin, Spring DI, DI native Gradle

=== Contexte

Le manifeste E-3PO (`doc/agentic_gradle_1-5.adoc`) proposait **PicoContainer**
(`org.picocontainer`, `DefaultPicoContainer`, `Caching()`) comme conteneur
d'injection de dépendances "zéro-magie" pour la couche IA du plugin.

_Problème_ : PicoContainer est-il pertinent pour l'assemblage des composants
de production (modèle LLM, mémoire vectorielle, agent) du plugin ?

=== État des lieux (audit 4 août 2026)

. **Zéro implémentation** : aucun import `org.picocontainer` dans le code source
  de slider-gradle (production ou test) ni dans aucun borough du workspace.
. **Absent de tous les catalogues** : aucun `libs.versions.toml` ne déclare
  `org.picocontainer:pico-container`.
. **Présence trompeuse** : `io.cucumber:cucumber-picocontainer` (7.34.3) est
  déclaré et consommé (via `libs.bundles.cucumber`, `testImplementation`) dans
  15 boroughs — mais c'est le module officiel Cucumber d'injection des
  `World`/`Steps` par scénario (BDD test), **pas** une DI de production.

=== Décision

**Ne pas utiliser PicoContainer comme conteneur DI de production.**

_Choix technique assumé_ : la DI native de Gradle (`@Inject`, `BuildService`,
`Provider<T>`, `Property<T>`) couvre déjà le besoin — injection par constructeur,
cycle de vie géré par Gradle, zéro dépendance runtime, isolation classloader
préservée (le premier ennemi des plugins Gradle). Le graphe de composants est
minuscule (~5 éléments) : un conteneur est de la cérémonie.

_Statut_ : cette décision reste en vigueur **jusqu'à réévaluation de la
situation** (par ex. graphe atteignant des dizaines de composants, dépendances
optionnelles runtime, ou abandon du modèle `BuildService`).

=== Critères de réévaluation

. Le graphe de composants IA dépasse ~15-20 services instanciés.
. Besoin de remplacement dynamique de dépendances au runtime (scoping).
. Migration hors `BuildService`/`Provider` Gradle (ex. agent autonome long-running).
. Si réévaluation : privilégier Koin ou Spring (maintenus) — PicoContainer est
  un projet sans mainteneur actif (dernière release stable ~2018).

=== Références

* Manifeste E-3PO : `doc/agentic_gradle_1.adoc` §4 (contexte de la proposition)
* Code existant : `slider/src/main/kotlin/slider/ai/RagTask.kt`, `AssistantManager.kt` (pattern DI native Gradle)
* Convention cucumber-picocontainer : `gradle/libs.versions.toml` (BDD test uniquement)

'''

== 📁 Decision 002 — Consommer codebase (N1) comme socle LLM unifié, ne pas réimplémenter koog/langchain4j

_Date_ : 4 août 2026  
_Statut_ : 🟡 EN COURS (cadrage — câblage slider non commencé)  
_Alternative considérée_ : ajouter `ai.koog:koog-agents` en direct dans slider (via BOM workspace-bom) + refaire le RAG

=== Contexte

Le manifeste E-3PO (`doc/agentic_gradle_1-5.adoc`) décrivait comme horizon :
* koog (orchestration agentique par graphe d'états)
* R2DBC (accès PostgreSQL réactif non bloquant)

_Problème_ : ces technologies ne sont pas un horizon vision — un socle N1 **déjà publié
sur Maven Central** existe dans les autres boroughs. Or les appels LLM de slider sont
éparpillés dans sa logique métier : `AssistantManager` (648 lignes, 4 factories de
modèles + dispatch `resolveModel` + pools), `RagManager` (282 lignes, RAG pgvector
refait), `OllamaLanguageModelAdapter` (client de traduction refait). Cette duplication
existe dans 8 boroughs de `foundry/public` (bakery, document, planner, plantuml,
newpipe, codex, codebase, slider).

=== État des lieux (audit 4 août 2026)

. **koog** (`ai.koog:koog-agents:1.0.0`, JetBrains, Apache 2.0) — implémenté en production :
  * codebase-gradle (N1, Central 0.0.5) : `VibecodingGraph`, `KoogPlanningOrchestrator`,
    `KoogAugmentedContextGraph`, `MultiChannelContextGraph`
  * document-gradle (N2) : `DocumentGenerationGraph`
  * Déclaré aussi : planner, capsule, codex, training, workspace-bom (agent/vibecoding-contracts)
. **R2DBC** — implémenté en production dans codebase-gradle :
  * `r2dbc-postgresql:1.0.7.RELEASE`, `r2dbc-pool:1.0.2.RELEASE`, `r2dbc-spi:1.0.0.RELEASE`
  * `R2dbcAgenticChunkRepository`, `AgenticChunkRepository`, `R2dbcInvalidChunkRepository`
. **EPIC L** (migration langgraph4j → koog) : ✅ TERMINÉ (codebase-gradle, sessions 034-049)
. **Gap consommateur (constat audit post-046)** : codebase n'expose **aucune API de
  consommation de services** — zéro `BuildService`, zéro `Provider<ChatModel>`, deps
  langchain4j/koog en `implementation` (non exposées au compile). La consommation
  documentée est *par tâches et fichiers* (`collectCompositeContext`,
  `exposure-manifest.json`), pas par injection.
. **Référence pilotage** : `office/pilotage/codebase/KOOG_AGENTIC_PATTERNS.adoc` (koog 1.0.0, maj 4 août 2026)

=== Décision

**Slider consomme codebase (N1) comme socle LLM unifié — il n'ajoute pas koog en
direct et ne refait pas de factories de modèles.** codebase est le premier consommateur
cible (pilote) de l'API de services que codebase doit exposer.

_Règles d'alignement_ :
* koog = orchestration (graphe d'états), langchain4j = exécution (LLM, pgvector, embeddings)
* Le `ChatModel` est obtenu par **injection de services** (`BuildService`/`Provider`,
  DI native Gradle — Decision 001), jamais par construction locale
* koog/langchain4j exposés par codebase en `api` → slider les consomme transitivement,
  sans déclaration directe via BOM (pas de duplication)
* Version koog pilotée par la BOM workspace-bom (1.0.0), résolue par codebase
* Premier usage cible : graphe d'orchestration `proposeDeckContext` → `generateDeck`
  (`DeckPipelineGraph`), exécuté sur les services codebase

=== Critères de réévaluation

. codebase n'expose pas le service LLM consommable (US-8.1 bloquée / refusée côté Queens)
. Le périmètre LLM de codebase (pool rotation, provider dispatch) ne couvre pas les
  besoins slider (streaming, providers cloud) sans lourdeur disproportionnée
. Le DAG N1 codebase (qui dépend de codex N2) n'est pas régularisé et crée un couplage
  inacceptable pour les consommateurs N2

=== Références

* Doc patterns pilotage : `office/pilotage/codebase/KOOG_AGENTIC_PATTERNS.adoc`
* Implémentations N1 : codebase-gradle `src/main/kotlin/codebase/koog/`
* Audit consommation : codebase-gradle `CodebasePlugin.kt` (aucun BuildService), `build.gradle.kts` (deps `implementation`)
* Vision : `doc/agentic_gradle_1.adoc` §1 (koog) et `doc/agentic_gradle_5.adoc` (R2DBC)
