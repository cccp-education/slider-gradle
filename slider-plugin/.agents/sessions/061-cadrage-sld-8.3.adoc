L'US-8.3 introduit une orchestration koog du pipeline deck via un graphe
`DeckPipelineGraph` qui chaîne les 3 nœuds : `propose-context` → `validate-context` →
`generate-deck`. koog gère la topologie (nœuds, edges conditionnels, state), langchain4j
exécute les appels LLM via `LlmProviderChatModelAdapter` (S-060).

== Travail effectué

=== 1. Consommation KOOG_AGENTIC_PATTERNS.adoc

Lecture intégrale du document `office/pilotage/codebase/KOOG_AGENTIC_PATTERNS.adoc`
(1781 lignes, 15 patterns koog 1.0.0). Points clés extraits :

- *Principe fondateur* : koog orchestre, langchain4j exécute
- *DSL koog* : `strategy<TIn, TOut>`, `node<In, Out>`, `edge(from forwardTo to onCondition {})`, `nodeStart`/`nodeFinish`, `ToolSelectionStrategy.NONE`, `asMermaidDiagram()`
- *State pattern* : data class Kotlin immutable, `copy()` par nœud
- *Patterns pertinents* :
  - Pattern 13 (Subgraphs) — composition de sous-graphes via `graph.invoke()`
  - Pattern 08 (Guardrails) — validation pure (pas de LLM) avant appel LLM
  - Pattern 05 (Routing) — edge conditionnel `onCondition { it.x }`

=== 2. Audit codebase (références existantes)

Audit des fichiers koog existants côté codebase-gradle pour identifier les patterns
à réutiliser côté slider :

- `codebase.koog.KoogAugmentedContextGraph` (141 lignes) — pattern hybride : graphe koog
  `strategy<AugmentedState, AugmentedState>` pour la topologie + méthode `execute()`
  séquentielle avec try/catch par nœud. **C'est le pattern de référence pour SLD-8.3.**
- `codebase.koog.state.AugmentedState` (20 lignes) — data class immutable avec 8 champs
  + `copy()`. Pattern pour `DeckState`.
- `codebase.koog.llm.LlmProvider` (10 lignes) — `fun interface LlmProvider { suspend fun call(prompt: String): String }`.
  Abstraction LLM de codebase, déjà wrappée côté slider par `LlmProviderChatModelAdapter`.
- `codebase.koog.llm.service.LlmBuildService` (54 lignes) — BuildService Gradle exposant
  `LlmProvider` via `LlmServiceResolver.resolveProvider()`. Déjà câblé côté slider
  (S-060, `registerLlmBuildService()`).

=== 3. Audit slider (état actuel du pipeline deck)

Audit des tâches Gradle existantes qui seront orchestrées par le graphe :

- `slider.ai.RagTasks.ProposeDeckContextTask` — tâche `proposeDeckContext` (step 1/2).
  Lit `-Psubject`, résout la langue (cascade 5 couches I18nConfigResolver), récupère
  le contexte RAG, appelle le LLM avec `PromptManager.contextSystemPrompt` +
  `contextUserMessage`, parse le JSON en `DeckContext`, écrit `*-deck-context.yml`.
- `slider.ai.RagTasks.GenerateDeckTask` — tâche `generateDeck` (step 2/2).
  Lit `-Pdeck.context`, charge le `DeckContext`, récupère le contexte RAG AsciiDoc,
  appelle le LLM avec `PromptManager.deckSystemPrompt` + `deckUserMessage`, écrit
  `slides/misc/<outputFile>`.
- `slider.ai.AssistantManager.PromptManager` — prompts system/user pour les 2 étapes.
- `slider.ai.LlmProviderChatModelAdapter` (49 lignes, S-060) — adapteur
  `LlmProvider` (suspend) → `ChatModel` (langchain4j) via `runBlocking`.

**Constat** : les 2 tâches sont indépendantes, aucun chaînage, aucune validation du
contexte proposé entre les 2. L'utilisateur doit manuellement enchaîner.

=== 4. Cadrage formel US-8.3

Rédaction du cadrage dans `slider-plugin/.agents/INDEX.adoc` (section EPIC SLD-8 US-8.3)
+ `BACKLOG.adoc` + `PROMPT_REPRISE.adoc`.

*Domaine DDD cible* : `slider.pipeline` (nouveau, 16ème domaine)

*Architecture cible* :
```
DeckState(subject, language, authorName, authorEmail, ragContext, deckContextJson,
           contextValid=false, validationError=null, deckAdoc="", error=null)

  [nodeStart] → [proposeContext] → [validateContext] → [generateDeck] → [nodeFinish]
                     ↑ LLM call            ↑ pure check        ↑ LLM call
```

*Edges conditionnels* :
- `validateContext → generateDeck onCondition { it.contextValid }`
- `validateContext → nodeFinish onCondition { !it.contextValid }` (error = validationError)
