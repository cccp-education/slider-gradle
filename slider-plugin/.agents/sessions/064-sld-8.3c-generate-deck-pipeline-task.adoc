== Décisions

. *Adaptateurs concrets côté `slider.pipeline`* : les 2 adaptateurs
  (`PromptManagerDeckPromptBuilder`, `ChatModelDeckLlm`) vivent dans le
  domaine `slider.pipeline` (pas dans `slider.ai`) — ils sont les ports-out
  du domaine, gardant le graphe koog pur. La dépendance vers `slider.ai`
  (`PromptManager`) et `langchain4j` (`ChatModel`) est assumée : ce sont des
  adaptateurs d'infrastructure, pas du domaine pur.

. *Prompt flat en `UserMessage` unique* : `ChatModelDeckLlm` envoie le
  prompt complet (system + user concaténés par `PromptManagerDeckPromptBuilder`)
  comme un seul `UserMessage`. Les modèles Ollama/langchain4j gèrent le prompt
  merged identiquement à system+user séparés. Contrat simple (string unique)
  garde `DeckPipelineGraph` libre de types langchain4j.

. *Tâche RAG-free* : `generateDeckPipeline` ne touche pas pgvector
  (contrairement à `proposeDeckContext`/`generateDeck`). Le RAG context
  optionnel passe via `-Pdeck.ragContext` (string). Le pipeline koog reste
  pur LLM orchestration — le RAG est une préoccupation des tâches existantes.

. *Mock-LLM fallback préservé* : `resolveModel` réutilise le fallback
  `-Pollama.baseUrl` → `createOllamaChatModel` legacy. Les tests
  fonctionnels `generateDeckPipeline with -Psubject but no LLM` utilisent
  `-Pollama.baseUrl=http://localhost:1` + `-Pollama.timeout=1` pour déclencher
  un échec propre sur le nœud propose (pas de réseau réel).
